## Implementation Summary

File and attachment APIs are implemented in `FilesController` and `AttachmentsController`. Artifact-version download is implemented in `ArtifactsController`.

Application enforcement is centered on `FileService`, `ArtifactService`, `FileAuthorizationService`, `ConfiguredFileUploadPolicy`, `LocalFileStorageService`, and `FileRepository`.

Storage implementation:

- Local filesystem storage is implemented by `LocalFileStorageService`.
- Storage keys are server-generated tenant/project/file paths.
- Object-storage provider names currently resolve to `UnsupportedObjectStorageService`; signed read URLs are not implemented for local storage.
- Docker Compose mounts local uploads at `/app/storage/uploads`.

Upload implementation:

- File upload endpoints require authentication.
- Uploads require the FileSharing feature, quota approval, owner resolution, and resource authorization.
- Extension, content type, non-empty body, and max-size validation are enforced by configured policy.
- Original filenames are normalized with `Path.GetFileName`, invalid filename characters are replaced, and long names are capped.
- Storage keys are generated by the server and do not come from user input.

Download implementation:

- File and attachment downloads call authorization before opening file storage.
- Deleted or inactive file objects return safe not-found failure.
- Download responses now set `Cache-Control: no-store, max-age=0`, `Pragma: no-cache`, and `Expires: 0`.
- Authorized metadata responses no longer return `storageKey`, `storedFileName`, or artifact-version `filePath`.

Audit/security logging:

- Successful file upload, download, delete, artifact upload, and artifact download paths write audit entries.
- Denied file/attachment metadata and download attempts now write metadata-only audit entries with generic summaries. They do not log file body, filename, storage key, signed URL, token, cookie, or message body values.
